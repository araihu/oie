# Reply composition and explicit room sessions

API 0.11 adds optional `SendMessage.replyToMessageId`, outgoing `Message.replyToMessageId` and explicit room-session reads/join/leave commands. Clients supply the canonical retained target UUID and authored text. The engine validates the target account/conversation and snapshots its sender, excerpt, compatibility quote and valid wire reference with the message, receipt and transactional outbox. It never accepts a browser-supplied quote or protocol ID as authority.

The resulting `Message.originalText` is the full transmitted body. `Message.reply.bodyText` is the authored response. The frozen target UUID remains available as `replyToMessageId` even if the original later becomes unavailable. Receipt reconciliation compares the authored body and target, preserving an uncertain operation key through reload and HTMX navigation. Reusing a key with a different target or text conflicts. Established send receipts replay before current room/target eligibility checks, so a later leave or source change cannot turn a successful acceptance into a second send.

The XMPP adapter emits [XEP-0461](https://xmpp.org/extensions/xep-0461.html) reply metadata and [XEP-0428](https://xmpp.org/extensions/xep-0428.html) fallback spans using Unicode code points. Reply support is advertised by the client; a server reply namespace is not a prerequisite. Direct references use validated sender-scoped IDs. Group references require verified room-issued [XEP-0359](https://xmpp.org/extensions/xep-0359.html) IDs. Missing or ambiguous references produce quoted text without a fabricated structured ID. Reference uniqueness and source content are checked again inside acceptance; the receipt retains the actual accepted plan. Queued work does not reselect another provider ID later.

Saved public rooms support explicit entry and leave. GET history/details/session and reply preparation do not join. A durable intent has its own UUID and revision, with compare-and-set mutation preconditions and stable operation keys. The protocol checks that the room already exists before directed presence and confirms its own session through self-presence, not an account connection or public occupant list. Group sends require both the current active intent and matching confirmed session. The database claim checks active intent and its revision atomically with the queued-to-dispatching transition.

Active intents reconnect with bounded retry. Explicit leave and revoked access persist, and stale callbacks cannot revoke or restore a newer intent. Participant-supplied errors cannot establish provider rejection. Own reflected room messages enrich the existing canonical outgoing message after account/conversation/body validation, without creating another send, unread event or source message.

The message menu prepares a quoted target in the composer. Removing that target preserves the typed response. Pending/uncertain sends freeze body, target and operation key. The room controls distinguish durable active intent, account connectivity and confirmed membership; an active offline room can queue work while dispatch waits. Room command retries keep their original key/revision. English and Brazilian Portuguese are included. Existing HTMX fragment navigation, exact original copying and per-device draft fallback remain in use.

This increment supports basic saved public rooms. Password input, room creation, invitations, moderation, attachments and end-to-end encryption are outside its scope. Migration 9 adds room-intent state and observation deduplication without resetting history checkpoints or existing source data. Before any downgrade to an older engine, drain or cancel pending room sends and back up the data; older engines do not implement these room-dispatch guards.

Generated CLI tests exercise reply sends and room session/join/leave/replay against the real native store with a disconnected adapter.

Development Prosody integration verifies actual direct and room XML, Unicode fallback, own-reflection deduplication, reconnect queues, explicit leave and revoked access. Tests use isolated development accounts and rooms, not the user's Suchat account.

`make check` passes, including vacuum, generated-code drift, golangci-lint with zero findings, formatting, vet, Go tests, generated CLI tests and Compose validation. Changed application, SQLite, HTTP, XMPP and web packages pass race tests. The development XMPP suite and real-engine browser workflow pass.

`reply-compose.cjs` covers quoted target preparation, cancellation without losing text, draft/target restoration across reload and HTMX navigation, uncertain-send receipt reconciliation, exact original copying, explicit room CAS/retry/leave, and pt-BR touch interaction with denied storage and zero WCAG A/AA violations. It is included in the Dagger browser stage. Existing host browser suites also pass, including fragment navigation and the account capability matrix.

Full Dagger completion remains unverified.

Checkpoints advanced normally as archive recovery continued. New live data remained intact during verification. It did not enter rooms or send messages through the user's account.
